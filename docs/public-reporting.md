# Public reports

The landing page and the QR code in communication setup link to `/report/chat`. When an administrator enables AI report chat, Mews offers current-location sharing in its first message and asks for useful observations; visitors can also describe the city and a nearby landmark. The Vercel AI SDK and its OpenAI Responses provider use three typed tools: `askQuestion` for a follow-up, `findLocation` for server-side place search, and `prepareReport` for a report review. Mews asks for a missing city/area or specific landmark in conversation. Each search uses one named place. After a failed search, a new landmark is searched on its own with the earlier city/area. The Worker removes apostrophes from landmark queries because Photon can otherwise miss possessive business names such as McDonald’s. Once both are known, the Worker resolves the named area and searches for that landmark inside the area’s bounding box. If the provider supplies no bounds, it requires matching town/neighborhood metadata and limits results to 10 km around the named area, or 5 km around an already selected pin. It returns at most three validated, distinct Photon/OpenStreetMap results for the visitor to choose. Results must contain the requested landmark words; a fuzzy name such as “Domino One Condominium” cannot stand in for “Dominos”. Results outside that area are discarded. An unresolved area never falls back to a worldwide landmark search. Empty results and service failures show the landmark and area already supplied, with a **Use this location description** action. Choosing it lets the visitor continue without a map pin. The last failed lookup is carried in application context, so repeating the same place does not repeat the map request or the same generic question. A chosen description and failed lookup survive a reply failure. Switching to the form retains that location description. The model receives the chosen description and is instructed to ask only for missing observations or prepare the report when it has enough information. Chat has no embedded address-search field. These tools cannot file a report. The visitor checks the details and confirms before the application submits it. When chat is disabled or unavailable, the link opens the standard form.

The separate `/report` form accepts a location, description, and urgency flag. A visitor can type the location or choose a place or pin on the optional map. Map search uses Photon and OpenStreetMap, or Google Maps when its local demo configuration is enabled. A report stores the visitor's pin coordinates or the Google Place ID; it does not store Google-supplied coordinates or formatted addresses. The team can open the submitted location from the report. Both routes work without an account or contact details and do not expose team colony records or locations.

Both routes provide the shared **Use my current location** button without opening a map. It requests one position only after a click, with browser permission, and reports denied access, timeout, and unavailable-location errors without clearing entered text. Chat asks whether that position is where the cats were seen before accepting it as the sighting location. The Worker can look up a nearby address, but keeps the exact device coordinates even if the address lookup fails. The form saves the pin only on submission and shows the reported accuracy. Editing its location text clears a device pin so it cannot silently point to the old place. Selected chat pins survive switching to the form. The model receives the chosen location label; coordinates stay in application context and are attached to a report only when the review uses that same label. A corrected location does not retain the old pin.

Chat messages are sent to OpenAI using the administrator's saved key and model. The request uses `store: false`; OpenAI's other data handling rules still apply. Administrators can edit the **Report chat system prompt** under **Configuration → AI analysis**, view the required application instructions, and restore the default prompt. Saved instructions apply to the next reply. The prompt changes tone and follow-up questions; app validation, access rules, and confirmation still apply. The report contains the description the visitor confirms, rather than a duplicate transcript. The chat allows up to eight visitor messages for AI turns and has per-visitor and per-location rate limits. Visitors can switch to the form if the assistant is unavailable.

Both the chat and the form accept up to five attachments, 10 MB each: JPEG, PNG, GIF, WebP, AVIF, audio, PDF, text, Word (`.docx`), or CSV. The shared upload component shows previews and removal controls. Files stay selected if an assistant reply fails, the visitor switches to the form, or the final send fails. Sending a chat message sends the current files to the Worker for AI review. A visitor can send files without message text. Photos and documents go to the Responses API; text and CSV contents are decoded as UTF-8; supported recordings go through transcription first. Chat and team analysis use the same file preparation. Chat lists files that could not be read or fully analyzed. AVIF and unsupported audio formats are kept for the team but cannot be analyzed. Analysis reads at most 25 MB per request and the first 40,000 characters of each text file or transcript.

Files added, removed, or replaced after a draft is prepared need another review before chat can confirm the report. Every AI turn receives the current file set. Files are saved to private R2 and linked to the report in D1 only after confirmation; a chat review does not create a saved report or stored upload. Team members use authenticated attachment routes to view the originals. Opening a submitted report includes supported attachments in team AI analysis.

Submissions appear as community reports in the team's Reports inbox. Team members can create a task or link and review a report in the normal workflow. Both routes offer optional follow-up contact before sending. A phone number is strongly recommended, with email as an alternative. Permission starts unchecked. If the sender opts in, at least one valid contact method is required. Turning permission off omits the contact details. Without contact details, the report stays anonymous. The private inbox shows the contact methods and direct phone/email links; follow-up happens outside Mews. No message is sent automatically. The inbox refreshes when a team member returns to the app and at regular intervals while it is open; it does not send notifications.

Administrators can enable a phone number and email address under **Configuration → Communication setup**. Enabled details appear as direct contact links on the public form; disabled details are not returned by the public API. Phone calls, texts, and emails are handled outside Mews and do not create inbox reports. The QR link uses the current site's address, so use the public site to create a code for distribution.

The Worker validates and limits each submission, checks that it comes from the site origin, and uses the `PUBLIC_REPORT_RATE_LIMITER` binding to limit submissions per source IP. Cloudflare may still process network information under its own policies; the form does not request a name. Optional contact details are stored separately from the report message, with the time permission was given. These fields are sent only on final submission, not in AI chat requests. The chat instructions direct visitors to these fields rather than collecting contact details in the conversation. Contact details persist through failed sends, report corrections, and switching to the form; a successful send clears them. Submission retries use an idempotency key and a hash of the normalized report and file contents to avoid duplicate reports or attachments. D1 writes the report and attachment rows in one transaction. Failed upload attempts remove objects that have no database reference.

Before deploying these features, apply migrations through `0032_public_report_contact.sql` to the target D1 database and deploy the Worker with the public report and chat rate-limit bindings. Apply migrations with a Cloudflare connection that has D1 access before deploying the Worker. The release CI token can deploy the Worker but cannot apply D1 migrations. Local development applies migrations during setup. No outbound alert is included.

The chat keeps keyboard focus while replies are pending. Classic form confirmation replaces the fields inside the same card, preserving its layout height; inactive fields become inert. The shared content transition respects reduced motion. Failed sends preserve entered text and the submission key for retry. Storybook contains isolated Stageshow rehearsals for both transactions under Demos → Report chat.
