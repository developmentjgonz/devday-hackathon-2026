# Administrator configuration

Active administrators can open **Configuration → Communication setup** in the workspace. Phone and email are off by default. An administrator can save a phone number or email address and choose whether to show each on the public report form. An enabled option needs a valid contact detail. Turning an option off hides it from the public form and public API but keeps the saved detail for later. Calls, texts, and emails go to the contact directly and do not appear in the Mews inbox.

The same page has a downloadable PNG QR code for the public report chat and a separate link to the report form. The QR code uses the current site's origin and is generated in the browser. Generate it on the public site before printing or sharing it. A localhost QR code works only on that machine.

The AI report chat is off by default. An administrator can enable it after saving an OpenAI key in AI analysis. It uses that key and model, and sends visitors' chat messages to OpenAI. The public chat has per-visitor and per-location request limits. When chat is disabled or its configuration is unavailable, the QR link opens the standard form. Visitors confirm the report in the chat before it is sent.

**Sign-in access** controls demo sign-in. When enabled, anyone who can reach the site can sign in using a designated fictional member account and view or change workspace data. Regular demo members cannot become administrators or sign in as real Google users. The code-protected administrator has full team, configuration, AI analysis, and autopilot access. The last Google administrator remains protected against removal. Turning the setting off immediately ends demo sessions, including code-protected administrator sessions. Google sign-in and local test sign-in have separate controls.

The setting starts off. To designate the four existing fictional accounts, an operator can apply `seeds/demo-accounts.sql` to the intended database after those accounts exist. `seeds/demo-administrator.sql` creates the separate demo administrator. The files do not attach demo identities to Google users or turn on demo access. Review the target database before running them. The demo administrator requires a strong `DEMO_ADMIN_CODE` Worker secret and rate-limited sign-in. To rotate the code, turn demo sign-in off, replace the secret, then turn it back on.

The AI section saves an OpenAI model name and API key. Saving does not validate them with OpenAI. It also exposes the **Report chat system prompt**. Administrators can change Mews's tone and follow-up questions, save up to 6,000 characters, or restore the default prompt. The next chat turn uses the saved text. A disclosure shows the required instructions appended by the application. These keep the model within the report task and explain the `askQuestion`, `findLocation`, and `prepareReport` tool contracts. The app still validates report data and requires visitor confirmation before saving. This prompt affects public report chat; team report analysis has its own instructions.

Team members can request report suggestions from the report review drawer. See [OpenAI API key setup](openai-key-setup.md) for the data sent, review flow, and deployment setup. People can submit a location, description, and optional attachments through the public report form without an account or contact details. Reports submitted through the form appear in the team inbox.

The configuration API requires an active administrator and same-origin writes. The OpenAI key is encrypted with AES-GCM before storage in D1. API responses contain only the key's status; they never return its value. Administrators can replace or remove it. The encryption key is a 32-byte base64 secret in the Worker's `CONFIG_ENCRYPTION_KEY` binding; it must not be committed or exposed as a `VITE_` variable. The API rejects key writes if secure storage is unavailable and accepts key writes only over HTTPS or local test sign-in.

## Local setup

`npm run dev:api` creates a random local encryption key when none is configured. It preserves existing environment values and uses `.dev.vars` if present; otherwise it adds the key to `.env.local`. When it generates a key, it keeps a local copy under `.wrangler/state/` for recovery. These locations are ignored by Git. Keep the key stable for as long as the local database contains encrypted keys. If a configured key already exists, the script leaves it unchanged. Restart a running local API after changing its environment.

## Deployment setup

Before administrators save an API key in a deployed environment, provide a unique random 32-byte base64 value as the Worker's `CONFIG_ENCRYPTION_KEY` secret. Use Cloudflare's [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/) for the binding, rather than a checked-in variable. Preserve the secret across deployments and back it up securely. Changing or losing it makes stored API keys unreadable; an administrator must replace those keys. Configure each environment separately, and never reuse the local key in production.

Apply the D1 migrations through `0030_report_chat_prompt.sql` before using the page. Deploy the `PUBLIC_CHAT_RATE_LIMITER` and `PUBLIC_CHAT_TOTAL_LIMITER` bindings before enabling chat. `npm run test:workspace` covers administrator access, public contact visibility, encrypted storage, key replacement and removal, prompt editing, attachments, missing or changed encryption keys, and local setup. `tests/ui/configuration.spec.ts` covers the page's main states in Storybook.
